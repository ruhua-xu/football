### 1. 为未来多竞彩市场预留 Market 抽象

MVP 仍然只实现胜平负 1X2，但领域模型和数据库不能假设系统永远只有 1X2。

请增加 MarketType / MarketKey 等抽象，并至少预留：

THREE_WAY
HANDICAP_THREE_WAY
CORRECT_SCORE
TOTAL_GOALS
HALF_FULL

当前 ThreeWayProbability、ThreeWayMarketOdds、ThreeWayFixedBonus 等强类型对象可以继续保留。

但是 OddsSnapshot 和 SportteryBonusSnapshot 需要考虑：

market_type
handicap_value

等必要字段。

尤其后续必须支持中国竞彩让球胜平负，例如主队 -1、+1。

MVP 暂时不要实现让球计算，只保证 Domain 和 Schema 不会阻止后续扩展。

### 2. FusionPolicy 不要只实现 QUANT_ONLY_V1

QUANT_ONLY_V1 可以继续作为 MVP 默认 baseline。

同时请实现或至少完整定义第二个简单确定性策略：

MARKET_QUANT_BLEND_V1

例如：

P_final = w * P_quant + (1-w) * P_market

其中 w 来自配置文件。

目的不是立即优化预测，而是确保 MVP 阶段已经实际验证 FusionPolicy 接口。

以后加入 P_llm 时不应修改 P_final 的上层调用方式。

### 3. 调整 LLM 输出边界

继续禁止 LLM 输出：

EV
stake
budget
P_final
fusion_weight
parlay_structure
ticket_role
最终 Ticket
最终 NO_BET

这些必须由固定程序计算。

但是允许 LLM 输出语义级比赛方向和剧本关系，例如：

preferred_outcomes
avoid_outcomes
counter_scenarios
scenario_relationships

例如：

主剧本为 HOME_WIN。

如果 HOME_WIN 失败，GPT 可以指出 DRAW 是最可能的 secondary scenario。

这只是语义判断。

Betting Engine 后续仍然必须根据 P_final、Sporttery Bonus、EV、风险和资金约束决定该方向是否成为投注候选。

即：

LLM 负责提出剧本。

固定程序负责决定是否值得下注。

### 4. 提前定义 Ticket 与 AtomicBet 的区别

MVP 仍然只实现简单 2串1。

但是请在 betting_model.md 和 Domain Design 中明确：

Ticket 是用户实际看到的一张顶层竞彩票。

AtomicBet 是复杂过关方式展开后的内部计奖组合。

例如未来：

3串4

可能展开为多个 2-leg / 3-leg atomic bets。

4串11同理。

MVP 暂时不实现 AtomicBet 数据库和复杂计奖逻辑，但当前设计不能假设一个 Ticket 永远只有一个简单联合概率。

请提前记录这一架构决策，以避免后续实现 3串4、4串11 时重构 Ticket 模型。

### 5. 正式 LLM 分析必须基于冻结 Evidence

请增加架构原则：

生产分析时，LLM 不应自行临时浏览互联网后直接形成 P_llm。

外部动态信息应该先由 Provider / Evidence Collector 获取并保存：

Evidence

* evidence_id
* category
* statement
* source_reference
* observed_at_utc
* available_at_utc
* confirmation_status
* reliability_level

然后冻结到 MatchContext，再传给 LLM。

流程应为：

External Source
→ Evidence Provider
→ Evidence Snapshot
→ MatchContext
→ LLM

这样才能保证历史分析可回放，并防止回测出现未来信息泄漏。

LLM 只能基于 as_of_at_utc 时已经 available 的 Evidence 进行判断。

### 6. 投注金额必须符合竞彩实际下注单位

继续使用整数分存储 Money。

同时明确：

base_stake_fen = 200

即竞彩基础投注单位为 2 元。

Multiplier 必须为正整数。

实际 stake 应尽可能通过：

atomic_bet_count × base_stake × multiplier

推导得到。

Optimizer 不应生成无法实际出票的任意金额，例如 17 元。

对于 MVP 的简单 2串1：

atomic_bet_count = 1

stake = 200 × multiplier

以后实现 3串4、4串11 时再根据真实子注数量计算。

奖金舍入继续通过版本化 PayoutPolicy 实现，不要使用普通 float round。
